# S4：成文与排版

S4把已经通过审校的技术路线写成一篇独立成立的公众号文章。内容深度来自机制、代码、步骤、失败路径和边界，不靠拉长开头与结尾。

## 文章形态

- 约五至七个大章节，章节数量由任务复杂度决定；
- 开头迅速给出真实问题、读者处境和阅读回报，不写长背景；
- 主体占全文大部分，沿作者带路的机制链或多轮小目标推进；
- 每一章解决一个问题，并自然留下下一章必须回答的问题；
- 关键判断可以一句一段，技术解释用完整段落，避免整篇同一种节奏；
- 结尾回到读者能做什么、怎样判断是否成功，用一个简单但有余味的判断收住；
- 不强制字数；如果内容不足，只扩充机制、实操、排障、验证和边界。

## 两遍成文

第一遍只沿已经验证的技术路线把事情讲清，不在写每一句时同时背诵禁令。先让目标、操作、观察、失败、机制、修复和结果自然发生。

完整初稿写完后，必须从头独立精修一次：

1. **说话位置**：每个“我做过、我发现、生产环境、实际效果”都能回到`narrative_position`或真实材料；无法证明的亲历语气改回准确边界。
2. **段落推进**：给每段确认一个主要作用。后一段必须新增操作、观察、机制、例子、边界或后果；只把上一段换一种说法时合并或删除。
3. **技术主干**：尽早写清谁对什么做了什么、系统发生了什么。术语、背景和代码只有在回答当前问题时保留。
4. **修辞姿势**：识别反复使用的先误导后翻案、整齐排比、连续设问、假口语和固定短句收尾。判断直接说，依据放在附近；真实的实验推翻旧判断时才保留判断变化。
5. **朗读节奏**：连续短句像清单时合并，长句吞掉操作顺序时拆开；动作和输出已经说明结果时，不再补一句抽象感叹。
6. **结尾试删**：分别试删最后两段。删掉后技术闭环和阅读余味都没有损失，就让文章提前结束。

这次精修由LLM结合全文判断，不建立固定中文禁词表，也不让脚本替作者决定风格。

## 技术讲解

至少交付：

- 它解决什么、不解决什么；
- 系统怎样工作；
- 一个最小验证或观察方法；
- 与常见相邻方案的关键差异；
- 适用条件、失败条件和选择建议。

## 实操抄作业

围绕多个小目标写出现场推进：

`想做什么 → 为什么第一次没成 → 怎样定位 → 怎样修复 → 怎样验收 → 怎样优化`

命令和代码嵌入叙事，不得把正文写成互不相干的步骤列表。代码块使用带语言标识的Markdown围栏；伪代码必须在正文中说明。

## 最终Markdown

写入`article/final_article.md`：

- 仅一个一级标题；
- 正文使用二级章节、必要的三级小标题、列表、引用、重点句和带语言代码块；
- 每个大章节恰好保留一个`<!-- IMAGE:section_N -->`位置标记；
- 可以保留S2/S3所需的内部机制标记供脚本校验，但转换HTML时必须全部清除；
- 使用性能、比例、规模、成本、排名或benchmark数字时，只能逐字采用`numeric_claims.publish_text`，并在对应内容前放置`<!-- DATA:N01 -->`；`omit`项不得发布；
- 不放脚注、来源清单、英文原文、账号名称或固定评论区召唤；
- 需要归因时自然写“官方文档”“项目维护者”“国外相关研究”等，不把文章写成资料罗列。

## HTML

运行：

`python skills/tech-article/scripts/markdown_to_wechat_html.py --topic-dir /absolute/topic/path`

只输出`article/final_article_copy.html`。要求：

- 正文及其他可见文字统一15px，代码块内的代码、行号和语言标签统一12px；
- 公众号可复制的内联样式，不依赖页面背景、外部CSS或脚本；
- 技术主题采用清晰、精致、克制的macOS式信息层次；
- 代码块像带圆角的代码编辑器，保留语言、行号和语法高亮；
- 有序列表连续递增，子标题和说明不被错误拆行；
- 图片位置与标题保持呼吸距离；
- HTML中不得出现构建注释、深度标记、脚注标记和来源尾注。
